# Luc UI — component inventory (V1.0)

Historical V1.0 family inventory and gap rationale. **This document is not a
source of truth for what the package exports, and its numbers are illustrative.**
Two generated artefacts are, and both are checked by a command that fails when
they drift:

| What you want | Where it comes from | Checked by |
| --- | --- | --- |
| Every public import path and its exported symbols | [component catalog](./COMPONENT_CATALOG.md), generated from the package barrels by `packages/ui/scripts/generate-catalog.mjs` | `pnpm --filter @luc/ui catalog:check` |
| Every documented entry, family, route and its props | the Showcase registry, `apps/showcase/lib/docs/generated/`, generated by `apps/showcase/scripts/docs-registry.mjs` | `pnpm --filter @luc/showcase docs:registry:check` |

That is `LEG-003`'s answer to "one component inventory": the hand-written rows
below are kept for the *rationale* they carry — why a family exists, what gap it
closes — and every count a reader might act on is printed by a generator instead.
`tests/unit/docs-inventory.test.ts` asserts both halves of this paragraph, so a
future edit cannot quietly turn this file back into a third list.

> **Before you build a local primitive, look for it here.** If a family below
> already does the job, use it. If it does not, say so in the pull request
> before adding a component to the package — the bar for a new family is a real
> product need, not a component count.

- Public surface: `packages/ui/src/index.ts` and the subpath entries in
  `packages/ui/package.json`.
- Showcase routes: `apps/showcase/app/**/page.tsx`, registered in
  `apps/showcase/lib/navigation.ts`.
- Tests: `packages/ui/src/**/*.test.ts(x)` (Vitest) plus the browser suite in
  `apps/showcase/qa/` (routes in `routes.mjs`, behaviour in `behaviour.mjs`,
  tiers in `docs/QA_WORKFLOW.md`).

Legend: **Export** = the public entry that exposes it · **Route** = the Showcase
page that documents it · **A11y** = the behaviour source that owns the semantics ·
**Tests** = unit coverage (`✓`) or none (`—`).

## 10. Comparison with mature component libraries

Read for **inventory**, not for adoption. Counts are of *families*, not visual
style, and every library below exposes more components than LUC because LUC is a
product system rather than a general-purpose kit.

| Library | License | What LUC takes from it | What LUC deliberately does not |
| --- | --- | --- | --- |
| [Radix UI](https://github.com/radix-ui/primitives) | MIT | The primitive layer LUC composes: Dialog, Popover, Tooltip, Select, ToggleGroup, Collapsible, Separator, DropdownMenu. | Its visual defaults, and any second primitive stack alongside it. |
| [React Aria Components](https://github.com/adobe/react-spectrum) | Apache-2.0 | The semantics of date, time and number input (segments, locale, ranges). | A parallel component system: LUC composes the pieces, not the styled set. |
| [Base UI](https://github.com/mui/base-ui) | MIT | Reference for menu/select/slider semantics. | Adoption — Radix already owns that layer. |
| [shadcn/ui](https://github.com/shadcn-ui/ui) | MIT | The sidebar/navigation architecture in V0.5 and the design-contract idea. | Copying styling; the Showcase is not a shadcn skin. |
| [Mantine](https://github.com/mantinedev/mantine) | MIT | Inventory comparison only. | Its breadth: LUC does not need a second date system, a CSS-in-JS runtime or 100 components. |
| [Chakra UI](https://github.com/chakra-ui/chakra-ui) | MIT | Inventory comparison; its `Slider`, `Accordion`, `Alert` informed the gap list below. | A style-prop system. |
| [Ark UI](https://github.com/chakra-ui/ark) | MIT | Headless-state architecture reference for the gaps in §11. | Adoption; it duplicates Radix's role. |

## 11. Gap audit — closed at V1.0

Each candidate was judged against the same threshold: a family is **MUST-HAVE**
only if it is a common primitive, would otherwise be reinvented per product,
carries complex accessibility behaviour, is already worked around ad-hoc, or is
very likely needed by the next product across multiple pages. Four cleared it at
V0.6; all four shipped at V1.0. Everything else stays classified below, with no
component invented merely for completeness.

### A. MUST-HAVE before V1.0 — shipped in this round

All four were implemented, documented in the Showcase, unit-tested and exported.

| Gap | Why it clears the threshold | Evidence in this repo today |
| --- | --- | --- |
| **Slider / RangeSlider** | *Shipped* → `@luc/ui/slider`. A continuous numeric control a form can use; neither ECharts' nor TradingView's slider is one. | `/components/slider`, `Sliders.test.tsx`, consumer scenario `slider` (6.2 KB raw). |
| **DropdownMenu / ContextMenu** | *Shipped* → `@luc/ui/dropdown-menu`, `@luc/ui/context-menu`. Row actions had no home; the Showcase built them out of buttons and a Sheet. | `/components/menus`, `menu.test.tsx` (9 cases incl. submenu, checkbox, radio, context trigger), consumer scenario `menus` (2.5 KB raw). |
| **Alert / Callout** | *Shipped* → `@luc/ui/alert`. Page-level notices had no surface; `Field` errors and toasts answer different questions. | `/components/alert`, `alert.test.tsx`, consumer scenario `surfaces`. |
| **EmptyState (generic)** | *Shipped* → `@luc/ui/empty-state`. The most predictable duplication in the next product; two near-identical implementations already exist inside the chart and table families (both kept, for domain wording). | `/components/empty-state`, `empty-state.test.tsx`, consumer scenario `surfaces`. |

### A′. The original evidence, for the record

| Gap | Why it cleared the threshold | Evidence before the round |
| --- | --- | --- |
| **Slider / RangeSlider** | A threshold, lookback or weight control is a common analytical input, and a keyboard- and touch-correct slider is not something a product team should hand-roll. Both ECharts and TradingView ship their own, but neither is a LUC control a form can use. | `RangeSelector` and the chart ranges are discrete buttons; the pattern pages have no continuous input at all. |
| **DropdownMenu / ContextMenu** | LUC already depends on Radix's menu primitives (Select, Combobox, Command) but exposes no plain menu with items, separators, shortcuts and submenus. Every product ends up building one for row actions. | The Showcase builds row actions as buttons plus a Sheet; the DataTable has no row menu. |
| **Alert / Callout** | A static, semantic message block (info / warning / danger / success) is expected on nearly every settings, research and data page. Today the only message surfaces are `Field` errors, `FormErrorSummary` and a toast — none of which is an inline page-level block. | Chart and table error states are chart/table-specific; page-level notices have no home. |
| **EmptyState (generic)** | LUC has `ChartEmptyState` and a table empty row, but no general empty surface for a page, panel or list. This is the most predictable duplication in the next product. | Two near-identical implementations already exist inside the chart and table families. |

### B. USEFUL LATER — 12 families

Legitimate general components with no evidence that Luc Web needs them
immediately. Each has a documented next step rather than an implementation.

| Gap | Why it is not V1.0 blocking |
| --- | --- |
| Accordion / Collapsible (public wrapper) | Radix `Collapsible` is already used by `SidebarSubmenu`; a public wrapper is thin sugar, and details/summary covers prose cases. |
| HoverCard | Rich hover previews are a product decision; the tooltip covers the timing-sensitive case. |
| Avatar / AvatarGroup | Trivial to compose from `Card` + tokens, and the next product has no identity surface yet. |
| Pagination (standalone) | `DataTablePagination` exists; a page-number control outside a table can wrap it when a page needs one. |
| Toggle / ToggleGroup (public) | `SegmentedControl` and `Switch` cover the real cases; Toggle is a styling variant of an existing button. |
| Kbd / Shortcut display | `Kbd` already exists (used by the command menu); only a shortcut-table pattern is missing. |
| Stepper / Steps | A settings or onboarding flow will decide its own shape; a generic stepper risks being wrong for the first real user. |
| Timeline | News and event streams are provider-owned today (TradingView Top Stories); revisit with a real LUC event source. |
| TreeView | Nested navigation stops at two levels by design; a file tree needs a real consumer. |
| Carousel | No product case; the motion grammar discourages it. |
| AspectRatio / ScrollArea | Tailwind utilities and `overflow` rules cover these; Radix `ScrollArea` would only add a styled wrapper. |
| Resizable (public primitive) | `Workspace` already wraps the engine; exposing the raw primitive invites ad-hoc layouts. |

### C. PRODUCT-SPECIFIC / DO NOT ADD YET — 8 families

| Gap | Why it must wait |
| --- | --- |
| DataGrid / editable cells | The V0.3 boundary is explicit: LUC formats, it does not edit. Editing needs a product's own commit, validation and undo model. |
| Drag and drop | No LUC surface accepts a drop today; the sidebar and workspace are deliberately fixed. |
| Masked input (card, phone, IBAN) | Region-specific, and every product that needs one also needs a validation library LUC will not adopt. |
| Upload progress | `FileInput`/`DropZone` never upload; progress belongs to the product's transport. |
| Multi-select Combobox | `FacetFilter` covers the filtering case; a multi-value Combobox should land with the first product that needs free-text multi-select. |
| Menubar | Desktop-application chrome; the AppShell's topbar is the product's own composition. |
| Product theme builder | The semantic layer already supports overrides; a builder is a product feature. |
| Project-symbol/navigation constants | `@luc/ui` must stay product-agnostic — see the V0.6 TradingView registry for how provider data *is* allowed to live in the package. |

No component from bucket B or C was implemented. V1 added exactly the four
MUST-HAVE families and stopped.

### V1.0 conclusion

Luc UI V1.0 is ready to be the foundation of the first real product consumer.
The evidence is in `docs/V1_API_AUDIT.md`, `docs/V1_TOKEN_AUDIT.md`, the test
suite, the package gates and the browser QA report — not in a score.

Nothing in the audit is a blocker. The four MUST-HAVE gaps are closed, the two
