# LUC UI V0.4 — open-source audit (forms, dates and inputs)

Researched **2026-09-26** for the V0.4 round (Forms + Date & Time). Every
license, version and last-push date below was read from the npm registry or the
GitHub API on that day; commands are recorded at the end. This is an
engineering assessment, not legal advice.

The rule for the round: **research widely, depend narrowly.** Six capabilities
were needed (form state, validation, date/time behaviour, number entry, OTP,
file selection). Two became dependencies, one was already in the tree, and three
were built on what we already ship.

## Summary of decisions

| Capability | Decision | What we took | What we left |
| --- | --- | --- | --- |
| Form state | **No forced engine.** LUC primitives + one optional React Hook Form adapter | The submit lifecycle, the error summary, field wiring | TanStack Form (documented recipe instead of an adapter) |
| Validation | **Standard Schema compatible, never required** | `rules`/resolver pass-through, server errors, async rules | Any Zod-specific concept inside `@luc/ui` |
| Date & time | **React Aria Components + `@internationalized/date`** | Calendar/range/time semantics, locale, keyboard, value types | React DayPicker, date-fns, a bespoke date model |
| Number entry | **React Aria `NumberField`** (already in the new dependency) | Locale parsing, caret safety, spinbutton semantics | `react-number-format` |
| OTP / PIN | **`input-otp`** | Paste, backspace navigation, one real input | Hand-rolled slot state machines |
| File selection | **React Aria `FileTrigger` + `DropZone`** | Picker semantics, drop target, keyboard path | `react-dropzone` |
| Tag input | **Built on our own `Input` + `Tag`** | Chips, commit keys, paste splitting | A fifth selection dependency |

## Form engines

### [TanStack/form](https://github.com/TanStack/form)

- License **MIT**, `@tanstack/react-form@1.33.5`, last push 2026-09-25, ~6.7k stars.
- **Strengths**: Standard Schema validation natively, typed field paths, derives
  state from a store rather than re-rendering the form, first-class arrays.
- **Weaknesses**: a young API with a higher rate of breaking change than React
  Hook Form, and a render-prop shape that makes a "field component" feel
  slightly different from the rest of LUC's composition style.
- **Verdict**: not chosen as the *adapter*. The render-prop API composes with
  LUC `Field` in about four lines (documented in `docs/FORM_GUIDE.md`), so an
  adapter would have added API surface without removing work.

### [react-hook-form/react-hook-form](https://github.com/react-hook-form/react-hook-form)

- License **MIT**, `react-hook-form@7.89.0`, last push 2026-09-26, ~44.9k stars.
- **Strengths**: uncontrolled by default (few re-renders), a decade of
  production use, `Controller` for controlled controls, `formState` covering
  dirty/touched/validating/submitting, and `@hookform/resolvers` (MIT) which
  now speaks Standard Schema — so Zod 4 and Valibot both work without LUC
  knowing either name.
- **Weaknesses**: the API is large; `register` vs `Controller` is a real
  decision for each control.
- **Verdict**: **chosen as the optional adapter** (`@luc/ui/forms/react-hook-form`).
  It is a peer dependency, so a product that does not use it never loads it.

### What LUC owns regardless of the engine

`Form` (one submit lifecycle, one status vocabulary), `FormErrorSummary` (a
summary that can move focus back to the offending field), `FormSection`,
`Fieldset`, `FieldGroup`, `FieldArray`, and the `Field` wiring that turns a
label, a description and an error into one accessible control.

## Date and time

### [adobe/react-spectrum](https://github.com/adobe/react-spectrum) — React Aria Components

- License **Apache-2.0** (`react-aria-components@1.21.1`,
  `@internationalized/date@3.12.4`), last push 2026-09-26.
- **Strengths**: the only studied option that treats *date-only*, *local
  date-time* and *zoned date-time* as different value types; real locale data
  (first day of week, non-Gregorian calendars, 12/24-hour clocks, numeral
  systems); calendar, range calendar, date field, date picker, date-range picker,
  time field and number field with proper ARIA; min/max, `isDateUnavailable`,
  anchored range selection; date arithmetic that is DST-safe.
- **Weaknesses**: a large package (unstyled, so shipping it means shipping its
  behaviour layer), and its own opinions about props (`isDisabled`, `onChange`)
  which we translate into LUC's vocabulary.
- **Verdict**: **adopted as the date/time foundation.** LUC owns every pixel —
  the header, cells, range band, month/year jump and popovers are ours.

### [gpbl/react-day-picker](https://github.com/gpbl/react-day-picker)

- License **MIT**, `react-day-picker@10.0.1`, last push 2026-08-26, ~6.9k stars.
- **Strengths**: pleasant API, range and multi-month support, a big customisation
  surface, few opinions about markup.
- **Weaknesses**: values are JavaScript `Date` objects — the exact ambiguity V0.4
  set out to remove — and there is no time field, no zoned value and no
  segmented editing, so half the round would have needed a second system.
- **Verdict**: not adopted.

### [date-fns/date-fns](https://github.com/date-fns/date-fns)

- License **MIT**, 4.4.0 (npm metadata; GitHub's license detector does not
  recognise the repo's split license files), last push 2026-09-22.
- **Strengths**: excellent formatting/math helpers, and `@date-fns/tz`.
- **Weaknesses**: only makes sense with a `Date`-based model, which is what we
  deliberately avoided.
- **Verdict**: not installed. Formatting is `Intl` through
  `@internationalized/date`'s `DateFormatter`, wrapped in LUC helpers.

## Specialised inputs

### [guilhermerodz/input-otp](https://github.com/guilhermerodz/input-otp)

- License **MIT**, 1.5.0, last push 2026-09-10, ~3.3k stars.
- **Strengths**: one real `<input autocomplete="one-time-code">` behind visible
  slots, which is what makes paste, backspace-across-boundaries, screen readers
  and password managers behave. ~118 KB unpacked including maps.
- **Weaknesses**: its slot styling must be written from scratch (which is what
  we want anyway).
- **Verdict**: **adopted.**

### [react-dropzone/react-dropzone](https://github.com/react-dropzone/react-dropzone)

- License **MIT**, 20.1.2, last push 2026-09-20, ~11k stars.
- **Strengths**: mature handling of browser drag quirks and `accept` matching.
- **Weaknesses**: its hooks still expect us to own the whole visual layer, and
  React Aria's `FileTrigger` + `DropZone` already cover the picker, the
  keyboard path and the drop target with the semantics our date and number
  fields use.
- **Verdict**: not adopted; studied for rejection semantics (a rejected file gets
  a name and a reason, never silence).

### [s-yadav/react-number-format](https://github.com/s-yadav/react-number-format)

- License **MIT**, 5.4.5, last push 2026-03-22, ~4.1k stars.
- **Verdict**: not adopted. React Aria's `NumberField` already formats and parses
  through `Intl`, handles the caret, and gives us a real spinbutton; adding a
  second number engine would duplicate that.

## Newly discovered this round

- **[react-hook-form/react-hook-form#standard-schema](https://github.com/standard-schema/standard-schema)** —
  the missing piece that lets us say "any validator" and mean Zod, Valibot,
  ArkType or a hand-written `validate` function.
- **[adobe/react-spectrum `CalendarYearPicker` / `CalendarMonthPicker`](https://react-spectrum.adobe.com/react-aria/Calendar.html)** —
  React Aria 1.21 exposes year/month picker hooks; we used the pattern (a
  decade page plus a month grid) but rendered our own ARIA grids so the same
  components serve both the calendar header and the standalone pickers.
- **`@internationalized/date`'s value types** — `CalendarDate`,
  `CalendarDateTime`, `ZonedDateTime` and `Time` as four distinct things. This
  single idea removed the entire "date-only shifts by a day" class of bug.

## License findings that matter

1. Everything adopted this round is **MIT** (`react-hook-form`,
   `input-otp`) or **Apache-2.0** (`react-aria-components`,
   `@internationalized/date`). No attribution burden beyond keeping the
   installed packages' notices, plus the Apache-2.0 `NOTICE` files that ship
   inside the packages.
2. `@hookform/resolvers` (MIT) and `zod` (MIT) are Showcase-only dependencies
   used to prove the resolver path.
3. `ariakit` still has no root license file detectable by the GitHub API even
   though npm says MIT. It remains **reference-only**, so no obligation arises.
4. Nothing in this round was copied from an `MIT + Commons Clause` project, and
   nothing was copied from an unmaintained project.
