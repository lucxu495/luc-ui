## 2. Actual architecture

`luc-ui` is a self-contained pnpm workspace member (root `pnpm-workspace.yaml`:
`luc-ui`, `luc-ui/apps/*`, `luc-ui/packages/*`, `luc-web`). **OBSERVED**

```
luc-ui/
  packages/ui/          @luc/ui  — tokens, components, layout, motion, data,
                         forms, datetime, charts (ECharts + Lightweight
                         adapters), app-shell, workspace, url-state,
                         integrations/tradingview; compiled via tsdown
  packages/visuals/      @luc/visuals — static-first visual element library:
                         contracts, registry, elements/*, skins, art, styles
  apps/showcase/         Next.js 16 App Router "documentation site + studios +
                         visual QA target"  ← the product this audit is about
  docs/                  CHART_GUIDE, MOTION_GUIDE, DESIGN_SYSTEM.md,
                         AI_DESIGN_GUIDE.md, per-phase audits, research
  artifacts/             generated QA output (only baselines/ is tracked)
  skills/                in-repo Codex skills
```

Ownership boundaries that the audit confirmed in code (**SOURCE_ONLY**):

- The Showcase never deep-imports `luc-ui` sources; it consumes `@luc/ui` and
  `@luc/visuals` subpaths (`eslint` rule `luc/no-deep-package-imports`).
- `luc-ui` imports no backend project. Its only peer is itself.
- The Showcase owns: the navigation model, the docs registry, the playground
  adapters, the demos, the studios, the QA harnesses.

**Duplicated concerns found (this is where multiple sources of truth live):**

| Concern | Implementations | Notes |
|---|---|---|
| Component identity / routing | `lib/docs/taxonomy.ts` (curation) + `lib/docs/generated/{registry,nav,api}.ts` (generated by `scripts/docs-registry.mjs`) + `luc-ui/docs/component-catalog.json` + `app/**/page.tsx` files | One generator + one checked-in projection; hand-written pages win over the dynamic route by Next's static-first resolution |
| Navigation | `lib/navigation.ts` (tree) + `lib/discovery/areas.ts` (areas) + `lib/discovery/taxonomy.ts` (use cases, art directions) + `siteMap` built inline in `app-frame.tsx` | Deliberately split (tree/area/data), but four places must stay in sync |
| Visuals catalog | `packages/visuals/src/registry/elements.ts` (contracts) + `apps/showcase/lib/visuals/catalog.ts` (view model) + `lib/visuals/families.ts` (browsable families) | Two vocabularies: contract family vs browsable family, mapped in `catalog.ts` |
| Charts catalog | `components/charts/chart-catalog-data.ts` (the registry the page and the verifier both read) | Single source; verified by `scripts/chart-catalog.mjs` |

## 5. Navigation structure

The navigation model is one tree with four consumers (header, sidebar, mobile
drawer, ⌘K palette) plus two derived axes. **SOURCE_ONLY + OBSERVED.**

| Layer | Implementation | Live observation |
|---|---|---|
| Global product nav | `components/shell/global-nav.tsx` — one `<Link>` per primary area plus a separate `aria-expanded` disclosure button; panels list that area's groups (`PANEL_ITEM_LIMIT = 9`) | Header on `/visuals/elements`: `Components · Visuals · Charts · More · Search ⌘K`; Visuals marked `aria-current` |
| Sidebar | `sidebarForArea(area, groups)` — only the current area's declared groups | `/visuals/elements` → 4 rows; `/components/buttons` → Components families; `/docs` → 41 links across 6 groups |
| Same-page anchors | `components/docs/page-outline.tsx` — an "On this page" rail built by scanning **every `h2,h3` inside `main`** | `/visuals/elements` → 55 entries; `/motion` → 32; `/charts/line-chart` → 14; `/components/accordion` → 11 |
| Breadcrumbs | `components/doc-pages/docs-breadcrumbs.tsx` from URL + registry | "LUC UI / Components" on a component page |
| Previous/next | `rel="prev"`/`rel="next"` links: **none found** on doc entry pages | `/components/accordion` has no pager; the only footer element is a version strip |
| Explore axes | `useCaseGroup` (8) and `artDirectionNavGroup` (6) — rows that link `/explore/browse?use=…` / `?art=…` | Sidebar on `/explore` shows "By use case" and "By art direction" |
| Language-specific routes | Locale handled by `stripLocale`/`href` in `lib/i18n`; zh coverage is enforced by `scripts/i18n-coverage.mjs` | Language control present in the header |

### 5.1 Navigation defects verified

**N1 — The right-hand outline harvests headings from *demo content*, not from
page structure. OBSERVED, root cause confirmed in source.**

`PageOutline` runs `root.querySelectorAll("h2, h3")` over `main` and slugs the
text. Live consequences:

| Page | Outline entries that are demo/specimen content, not page sections |
|---|---|
| `/components/accordion` | `#one-section-at-a-time`, `#ingestionok`, `#analytics7`, `#serving`, `#one-surface-many-sections`, `#is-the-panel-animated`, `#does-collapsing-unmount-the-content`, `#a-disclosure-without-an-item` |
| `/motion/spatial` | `#analyst-eu-west`, `#q3-review-the-compact-face`, `#apac`, `#built-for-dense-interfaces`, **`#built-for-dense-interfacesbuilt-for-dense-interfaces`** (a mangled duplicate) |
| `/visuals/elements` | all 45 element names plus 7 family names → a 55-row rail |
| `/charts/line-chart` | `#workspace-or-tarball`, `#package-registry`, `#required-setup`, `#configuration`, `#ai` |

This is the most plausible mechanism behind the user's report that "clicking
inside some component pages unexpectedly navigates to unrelated components or
pages": the rail offers entries whose labels look like unrelated product
concepts ("Ingestion ok", "Analytics 7", "Serving", "APAC"), produced by whatever
sample data the demo happens to render. **No cross-*page* navigation was
reproduced from clicking a demo** (§7.3).

**N2 — Duplicate DOM ids on `/visuals/elements`. OBSERVED.** `metrics` and
`tables` each appear twice, because the family filter chip and the section
anchor both use the family id. Deep links and `getElementById` semantics are
ambiguous.

**N3 — The outline duplicates the catalog.** On `/visuals/elements` the rail
lists all 45 capabilities while the page itself already groups them by family;
the rail is a second, weaker copy of the page. On `/motion` the rail lists 32
items. **OBSERVED.**

**N4 — Header responsive duplicates (checked; not a defect).** The header
contains two `Search ⌘K` controls, but a viewport check shows only one is
visible at a time (desktop trigger hidden at 390 px, mobile `Search`-labelled
control hidden at 1440 px), and the same applies to the primary nav links and
`Open navigation`. **OBSERVED — reclassified as correct responsive behaviour; no
action item.**

### 5.2 Navigation behaviour that is correct (do not "fix")

- Sidebar items are real destinations; **no same-page anchor is nested in the
  sidebar** anywhere observed. The Visuals group is four routes, not seven
  family anchors. **OBSERVED.**
- Active state resolves per area and per item (`aria-current` present once in
  the header on every route probed). **OBSERVED.**
- The ⌘K palette searches the whole tree rather than the current area, which is
  the stated intent. **SOURCE_ONLY.**
- Mobile: no horizontal overflow (`document.body.scrollWidth` 380 ≤ 390 at a
  390 px viewport on `/components/buttons`); the sidebar collapses and the
  header exposes `Open navigation`, `Show what is in Components/Visuals/Charts/
  More`, `Search`, `Switch language`, and motion controls. **OBSERVED.**

## 8. Workbench systems

Three distinct workbench implementations exist — **OBSERVED (source)**:

1. **`components/playground/**`** (component + chart specimens). `Control` is a
   closed union; `serialize` and the preview share one `values` object, so the
   code shown is generated from the same state the specimen renders. Two adapter
   registries (lightweight vs chart) keep engines out of primitive pages. 78
   adapters are wired. Control panels observed on `/components/buttons`:
   `CONTROLS` with `TITLE`, variants, sizes, icons, states.
2. **Studios** (`/studios/{charts,motion,themes,composer}`) — pure-logic modules
   in `lib/studios/*`, deterministic and unit-testable without a browser.
3. **Ad-hoc page-local control boards**, e.g. `/motion/spatial`'s single panel
   driving six families, and the `/visuals` style switcher.

**Workbench gaps verified OBSERVED:**

- No chart page positions its playground in the first viewport (§6.1).
- Control panels are labelled `CONTROLS` in caps and sit *below* the specimen on
  component pages; on chart pages they are below the fold entirely.
- There is no reset affordance on the `/components/*` playgrounds (a "Reset the
  demo" button exists only on the `/motion/spatial` board).
- No responsive-viewport control exists on any workbench (the `/motion/spatial`
  page has depth/tilt/orbit-speed but no width toggle).
- Visuals has no workbench at all, by explicit design decision
  (`lib/visuals/workbench.ts` header comment). This is a deliberate scope
  boundary, not a defect — but it means the `/visuals` "try it" journey is
  absent.
